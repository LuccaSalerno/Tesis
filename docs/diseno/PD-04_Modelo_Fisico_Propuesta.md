# PD-04 — Propuesta de modelo físico (para revisión)

**Estado:** incremento 1 **aprobado** por el equipo (Lucca Salerno, 22/10/2026) e implementado en la migración `0002`. Los incrementos de la §3 siguen como propuesta.
**Base:** tesis §5.2 y Figura 5.4; RF-03 a RF-07, RF-21, RF-25, RF-26; RN-09, RN-10, RN-14; RNF-04; PD-05; RC-P03; RC-P08.
**Alcance de PD-04:** tipos, fechas, índices y restricciones. No se quita ni renombra ninguna entidad o relación de la Figura 5.4; las columnas agregadas se marcan con **(+)**.

## 1. Convenciones comunes

| Tema | Decisión propuesta | Motivo |
|---|---|---|
| Nombres | Tablas y columnas en minúsculas con los nombres de la Figura 5.4 (`tramite`, `version_documental`, …), esquema `atlas` | Respetar los nombres de la tesis (AGENTS.md §4) |
| Claves primarias | `bigint GENERATED BY DEFAULT AS IDENTITY` | Figura 5.4. *Ajuste al implementar:* `BY DEFAULT` permite reservar con `nextval` el id de la versión inicial antes de insertar el documento que la referencia |
| Enumeraciones | `varchar` + `CHECK` con la lista cerrada, y `StrEnum` en Python. Sin tipos `ENUM` de PostgreSQL | La tesis pide enumeraciones (§5.2) y la figura usa `varchar`. Un `CHECK` se amplía en una migración sin recrear tipos |
| Fechas | `timestamptz`, en UTC. Columnas técnicas **(+)** `creado_en` / `actualizado_en` donde un RF pide fecha | RF-03, RF-21, RN-03 |
| Borrado | Ninguna tabla del dominio concede `DELETE` ni `TRUNCATE` a la aplicación. Única excepción propuesta: `usuario_rol` (§2.2) | RNF-04, RN-10 |
| Inmutabilidad | `version_documental` y `evento_auditoria`: la aplicación solo tiene `SELECT` e `INSERT`, y un *trigger* rechaza `UPDATE`, `DELETE` y `TRUNCATE` para **cualquier** rol | RF-05, RN-10, SEG-03 |
| Concurrencia | Las operaciones que cambian el estado del trámite toman `SELECT … FOR UPDATE` sobre su fila. Las restricciones únicas resuelven las carreras residuales | PD-05.2 y §5.2 («solo una puede completarse») |

## 2. Incremento 1 — núcleo (migración `0002`)

Cubre lo que necesitan los hitos 1.2 y 1.3: usuarios y roles, trámite, archivo, documento, versión y auditoría.

### 2.1 `usuario`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK |
| identificador_externo | varchar(128) | `UNIQUE`, **NULL solo si está suprimida** (sub de Cognito) |
| estado | varchar(20) | `CHECK IN ('habilitada','deshabilitada','suprimida')`, por defecto `habilitada` |
| autorizacion_cierre **(+)** | boolean | `NOT NULL DEFAULT false`. Ver pregunta P1 |
| creado_en / actualizado_en **(+)** | timestamptz | `NOT NULL DEFAULT now()` |

- `CHECK ((estado = 'suprimida') = (identificador_externo IS NULL))`. La supresión borra el dato identificatorio y conserva el `id` interno (RF-25).
- No se guardan nombre ni correo, que quedan en Cognito (minimización de datos).

### 2.2 `usuario_rol`
| Columna | Tipo | Restricciones |
|---|---|---|
| usuario_id | bigint | PK compuesta, FK `usuario` |
| rol | varchar(30) | PK compuesta, `CHECK IN ('responsable_tramite','revisor_aprobador','administrador_operativo')` |

- La tabla representa los roles **actuales**. Quitar un rol borra la fila, por eso esta tabla es la única con `DELETE` para la aplicación.
- El historial de otorgamientos y retiros queda en `evento_auditoria` (RF-25, RF-21).

### 2.3 `tramite`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK (el «identificador» de RF-03) |
| responsable_id | bigint | `NOT NULL`, FK `usuario`, índice |
| estado | varchar(30) | `CHECK IN ('borrador','pendiente_validacion','pendiente_aprobacion','observado','aprobado','cerrado','cancelado')`, por defecto `borrador` |
| titulo **(+)** | varchar(200) | `NOT NULL`, `CHECK (btrim(titulo) <> '')`. Decisión del equipo (P2) |
| descripcion **(+)** | text | Opcional (NULL). Decisión del equipo (P2) |
| motivo_cancelacion **(+)** | text | `CHECK ((estado = 'cancelado') = (motivo_cancelacion IS NOT NULL))` |
| creado_en / actualizado_en **(+)** | timestamptz | `NOT NULL` (RF-03) |

- Las **transiciones** (Tabla 3.VI) se validan en el dominio de Python, no con *triggers*. El `CHECK` solo garantiza que el valor pertenezca a los siete estados de la tesis.

### 2.4 `archivo`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK |
| tramite_id | bigint | `NOT NULL`, FK `tramite`, índice |
| clave_objeto | varchar(1024) | `NOT NULL UNIQUE` |
| huella | char(64) | `NOT NULL`, SHA-256 en hexadecimal minúsculo (`CHECK` por expresión regular) |
| estado_incorporacion | varchar(20) | `CHECK IN ('pendiente','incorporado','descartado')`, por defecto `pendiente` (RF-04, RF-07) |
| nombre **(+)** | varchar(255) | `NOT NULL`: metadato requerido en la carga (§3.3.3) |
| formato **(+)** | varchar(10) | `CHECK IN ('pdf','docx')` (RC-P04) |
| tamano_bytes **(+)** | bigint | `CHECK (tamano_bytes > 0)` |
| cargado_por_id **(+)** | bigint | `NOT NULL`, FK `usuario` (§3.3.3: usuario que realiza la carga) |
| cargado_en **(+)** | timestamptz | `NOT NULL` (§3.3.3: fecha de carga) |

- La aplicación solo puede hacer `UPDATE` sobre `estado_incorporacion`, mediante un privilegio por columna. `clave_objeto`, `huella` y los metadatos de carga quedan fijos.
- *Ajuste al implementar:* en `documento`, la aplicación solo puede actualizar `tipo`, `nombre` y `version_vigente_id`; un documento no cambia de trámite.

### 2.5 `documento`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK |
| tramite_id | bigint | `NOT NULL`, FK `tramite`, índice |
| tipo | varchar(20) | `CHECK IN ('contrato','presupuesto','orden_compra','factura','comprobante')`, **NULL hasta validar la clasificación**. Ver pregunta P3 |
| nombre | varchar(255) | `NOT NULL` |
| version_vigente_id | bigint | `NOT NULL UNIQUE` |

- La FK compuesta `(id, version_vigente_id) → version_documental(documento_id, id)` es `DEFERRABLE INITIALLY DEFERRED`.
- Con ella, cada documento tiene **exactamente una** versión vigente y esa versión **pertenece al propio documento** (§5.2). Documento y versión inicial se crean en la misma transacción.

### 2.6 `version_documental`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK; `UNIQUE (documento_id, id)` como destino de las FK compuestas |
| documento_id | bigint | `NOT NULL`, FK `documento` |
| archivo_id | bigint | `NOT NULL UNIQUE`, FK `archivo`: un archivo da lugar a una sola versión, como marca la figura |
| version_previa_id | bigint | `UNIQUE`; FK compuesta `(documento_id, version_previa_id) → (documento_id, id)` |
| numero | int | `NOT NULL`, `CHECK (numero > 0)`, `UNIQUE (documento_id, numero)` |
| creado_en / creado_por_id **(+)** | timestamptz / bigint | `NOT NULL`, FK `usuario` (actor que confirma, RF-07) |

- `CHECK ((numero = 1) = (version_previa_id IS NULL))`.
- `UNIQUE (version_previa_id)`: si dos confirmaciones intentan reemplazar la misma versión, solo una se completa (§5.2) y el historial queda lineal.
- Un *trigger* de inserción verifica que el archivo pertenezca al mismo trámite que el documento y que esté `incorporado`.
- La tabla es inmutable (§1).

### 2.7 `evento_auditoria`
| Columna | Tipo | Restricciones |
|---|---|---|
| id | bigint identity | PK |
| tramite_id | bigint | FK `tramite`, **NULL** si la acción no se relaciona con un trámite (§5.2) |
| actor_id | bigint | FK `usuario`, **NULL solo** cuando el actor es el sistema |
| actor_tipo **(+)** | varchar(10) | `CHECK IN ('usuario','sistema')`, más `CHECK ((actor_tipo = 'usuario') = (actor_id IS NOT NULL))` |
| version_id | bigint | FK `version_documental`, NULL si no corresponde (RF-21) |
| entidad_tipo / entidad_id | varchar(40) / bigint | `NOT NULL` |
| accion | varchar(60) | `NOT NULL`: código fijo del catálogo de acciones en Python |
| resultado | varchar(20) | `CHECK IN ('exito','rechazo')` |
| ocurrido_en **(+)** | timestamptz | `NOT NULL DEFAULT clock_timestamp()` (instante, RF-21) |
| solicitud_id **(+)** | uuid | Correlación con `X-Solicitud-Id` (RC-P01-002) |

- Índices `(tramite_id, ocurrido_en)` para la línea de tiempo (RF-22) y `(entidad_tipo, entidad_id)`.
- Sin texto libre: los motivos viven en su entidad (`decision.motivo`, `tramite.motivo_cancelacion`).
- La tabla es inmutable (§1).

### 2.8 Pruebas del incremento (PostgreSQL real)
Cada regla tiene al menos una prueba negativa:
- **RF-05:** versión inmutable; vigente obligatoria y del propio documento; dos versiones con la misma predecesora; coherencia entre `numero` y predecesora.
- **RN-10 y SEG-03:** `UPDATE`, `DELETE` y `TRUNCATE` de eventos rechazados, también con el usuario de migración.
- **RNF-04:** la aplicación no tiene `DELETE` sobre trámite, documento, versión, archivo ni evento.
- **RF-26:** cancelación sin motivo rechazada.
- **RF-25:** cuenta suprimida con identificador rechazada.
- **RC-P04:** formato fuera de la lista rechazado.
- **Archivo:** `clave_objeto` y `huella` no se pueden modificar.

- *Ajuste al implementar:* la aplicación queda con solo lectura sobre `alembic_version` (mínimo privilegio, RNF-01).
